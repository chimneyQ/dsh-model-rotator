# Changelog (dsh-model-rotator)

User-visible changes, newest first. Commit hashes in brackets.

## 0.2.22
- **Fixed: the publish loop could leave a version listed without a tarball.** 0.2.21 reached `latest` while its tarball answered 404, so `npm install dsh-model-rotator` would have failed even though the registry advertised the version. Versions are immutable on npm, so the broken entry cannot be withdrawn; 0.2.22 carries identical code and a fresh version number. No behaviour changed.
## 0.2.21
- **Changed: a route is now what a route always read like - several models aggregated into one entry.** Declaring a chain and marking it active used to change only the *order behind* the model the turn started on: the session model was always dispatched first, so the chain could not actually run the conversation, and a reader who built a free-model pool and switched it on kept getting the paid model as the first call every turn. That is an ordering hint, not an aggregation. With a route in force the turn now starts from the route's head: the first usable member answers, `fallback` restarts there every turn, `round-robin` advances by `stickyLimit`, and the session model keeps its seat immediately behind the pool - never dropped, only reordered. The switch record and the in-conversation notice name the candidate the walk actually displaced (previously they blamed the session model for a failure that had not even been dispatched yet). The pin keeps its meaning and now also keeps its *dispatch*: a healthy pinned model really is the first call, where the old walk listed it first and silently ran the session model instead.
- **Fixed: the member picker offered models that can never be dispatched.** Vision twins (`*-vision`, the image pipeline dsh-vision-router wraps around a chat model) are excluded from failover by the shipped rule, but the route editor's multi-select list and its autocomplete datalist still offered them - so building a pool by ticking produced members that every report then named under `not dispatched`. Both lists now read the server's own `kind` answer; a twin cannot be ticked into a route any more than it can be switched to. Members already saved as a twin keep working as before (still reported, still not dispatched); the fix is at the point where the mistake used to be made.
- **Added: the settings page is sorted into tabs.** Sixteen numbers and six switches in one scroll, under a 900-row roster and a route editor, meant every answer cost a hunt. Five panels now: Master (the switch, what is announced, the window guard, adoption, image turns), Switch policy (candidates, retries, backoff, consent, same-model preference), Cooldown and breaker (every timer and the threshold), Model list, Routes. Two decisions carry the design: a field's tab is data on its spec (a field nobody assigned throws instead of silently leaving the page), and the tabs answer by VISIBILITY only - the roster, its fetches and folds, and the route editor with its unsaved drafts stay mounted under every tab, because a panel that vanishes on a switch loses the chain the reader was mid-way through arranging. The page opens on Master: a settings page opens on settings.
- **UI: the page was reviewed as visual design, as interaction, and as experience; six real defects came out of it.** Small secondary text sat at 0.55-0.72 opacity at 11-12px and washed out on dark themes - the class is lifted to 0.7-0.82 and the warning orange to full alpha. A disabled button looked exactly like a live one (full opacity, pointer cursor): during a save, and on the up arrow of the first row, every control still invited the click that would be ignored. One composed `buttonStyleFor(disabled)` answers it at all 13 sites, and the bare reorder arrows now carry a hover title and an accessible name. A failed roster read ended in a dead sentence; the retry button now sits *at the error*, not in a header that scrolls away. The route editor wrote `Routes saved` and `Could not switch the route` in one identical grey line - the note now carries its tone (green for the save that worked, red for the one that did not). Monospace deliberately stays the roster row signature: a first attempt to dress member ids in the id-face was reverted, because that face is how the page tells a model row from a route row.
- **Tests: offline 248 -> 251, client 120 -> 132 (2 on the picker not offering twins, 3 on the disabled affordance and the arrow names, 7 on the tab bar: five named panels, the default tab, eighteen field panes kept mounted, the sibling panels, the swap, and the roster returning), settings 35, release gate 23, all green.** 25a/25c/25c2 rewritten to read the *dispatch order* of the aggregation (head = the route's first member), the pin assertion now proves the pin is dispatched first, 25d4/25d5 prove a declared vision twin member is neither dispatched nor hidden from the `not dispatched` report, 25l proves the switch record names the displaced candidate rather than the session model, and 5y2b/5y2c prove neither the picker nor the datalist offers a twin.

## 0.2.20
- **Fixed: pressing Stop was booked as the model failing.** When the caller cancels a turn (Stop, a deadline, a closed client) the provider answers with a `kind: 'aborted'` finish, and the walk priced it as a route failure: attempts/failures +1, consecutiveFailures +1, a network-shaped cooldown. Five cancellations in a row reached the breaker threshold (5 by default) and rested a perfectly healthy model for six hours - it had not failed again, somebody had stopped it. A cancelled attempt is now discarded instead of priced: no attempt, no failure, no run of failures, no breaker, no switch record. The test is deliberately narrow - the finish kind is `aborted` **and** the caller's own signal is already aborted - so an upstream that quits on its own is still a failure worth recording. Cancellation is also the one event that says nothing about connectivity, so it must not drag the score down either.
- **Fixed: a provider stream that threw switched the plugin off.** Everywhere else the walk survives a dead route; here `iterator.next()` throwing (`socket hang up`, `ECONNRESET`, a gateway closing mid-stream) sent the exception straight out of the generator to the caller. That is the most common way a route dies, and it was the one place failover never ran. The throw is now held and treated exactly like a content-free failure: same retry inside the attempt, same move to the next candidate. **Unless text has already flowed** - then it propagates untouched, because replaying it would duplicate the answer. When nothing can answer, the caller gets its own original exception, not a paraphrase written here, so the error surface of a failed turn is unchanged.
- **Fixed: a stream that simply ended, without a finish chunk, swallowed what it had already delivered.** Everything before the first content chunk (`block-start`, `usage`) is held back until it is known whether the attempt failed and has to be retried. The held buffer was flushed on the failure branch and on the abandon branch, but not on the "the provider stopped talking" branch: the stream ending is not an error, so the loop simply exited and the held chunks went out of scope with it. A provider whose stream closes without a finish therefore left the caller with an empty turn. The branch is now explicit - a stream ending is a normal end, and what was held is handed over - and the suite asserts it, which it never did: 2a only ever asserted what the caller must *not* receive.
- **Fixed (performance): an expired roster no longer blocks the turn.** The first turn after a process start, and (once the 60-second TTL lapsed) every turn after it, awaited a synchronous `listProviders()` plus one `listModels()` per provider walk. **Measured on this install: 482 provider/model pairs, about 15 seconds cold against 6ms warm** (`model_rotator_status`, 2026-11-16) - so roughly one turn a minute paid the whole sweep before its first token. That is the exact stall this plugin exists to remove, caused by the plugin itself. The roster is now stale-while-revalidate: the list already known is served at once and the refresh happens behind the turn. A refresh that fails keeps the known list instead of replacing it with an empty one, because an empty list is what silently disables failover.
- **Fixed (performance): one wedged provider can no longer stall the sweep.** `listModels()` is often a network call - an aggregate gateway's catalogue, a vendor's `/models` - and the sweep was sequential and unbounded. Each provider's roster call is now capped at 8 seconds: a provider that overruns contributes no rows to that sweep and the walk moves on. The first sweep a process needs is capped at 5 seconds **for the turn**: past it the turn runs on the plain harness path and the sweep finishes behind it. A sweep that overran is not waited on a second time, so a hung adapter costs one turn's budget once rather than every turn, and a turn whose roster is already known never waits for a refresh at all.
- **Fixed (performance): the context window was resolved again on every turn.** The window guard asked `resolveModelInfo()` for every candidate route on every walk - 240 adapter calls per turn on a 240-row synthetic roster, and 482 rows here - to read a number that only changes when a catalogue re-publishes. The answer is now cached for 5 minutes (measured: 240 calls on the first turn, 0 on the second). An entry that resolves to 0 is re-asked exactly like an absent one, so a catalogue that starts publishing a window is picked up on the next walk.
- **Fixed: four real failure sentences sat unclassified.** Taken verbatim from this install's `stats.json` and re-run against the classifier: 豆包's `还没有浏览器登录态。请在豆包卡片里点「重新登录」扫码一次。` is `auth` (a re-login really does recover it, so it keeps retries rather than earning a six-hour retirement); `raccoon: 您的模型请求频率超限，请稍后重试` and `qoder: 排队等待超时` are `rate-limit` (a queue timeout is a rate wall in another accent); `no adapter registered for provider "workbuddy"` is `unsupported` - this host registered no such provider, so the id can never be read and the answer is the same every time, which is a dead route rather than a half-hour backoff.
- **Tests: offline 230 -> 248 (18 new), client 120, settings 35, release gate 22 -> 23, all green.** The new assertions are grouped by scenario: 26a-26d a cancelled turn is charged to nobody and five in a row do not trip the breaker, 27a a stream that just ends still delivers what it held, 28a-28b a window is resolved once and then reused, 29a-29c a stale roster does not block the turn and is refreshed behind it, 30a-30b a throwing stream fails over and rethrows its own exception when nothing is left, 31a-31d the four real sentences above, 32a-32b a wedged adapter is capped by the first-sweep budget and not paid twice.
- **29x nearly shipped a hole it could not see.** Asserting only a *slow* sweep, the whole family stayed green while a *hung* one would still have blocked a turn once: the budget was there, the bypass that stops the next turn paying it was not. 32a/32b are the pair that closes it (3010ms cold, 0ms on the next turn, measured).

## 0.2.19
- **Added: multi-select member adding.** Previously one at a time: type an id and press Enter, or pick one from a datalist. Building a chain is really "I want these three", so that is now one action. *Pick several* opens a panel with a filter box (provider/model substring), lists only the models not already in the route, and adds every ticked one on *Add selected (N)*. Past 200 entries the list shows the first 200 and says to narrow the filter - a full 500-pair roster is a scrollbar nobody can aim at.
- **Added members are appended in roster order, not tick order.** Two people building the same chain from the same roster should end up with the same order, and tick order is invisible in the result; letting it decide the order manufactures a difference nobody can explain.
- Client assertions 114 -> 120 (picker opens and closes, only un-added models listed, filtering keeps the ticks, the button counts them, one action appends, the panel closes after adding).

## 0.2.18
- **Added: route chains (`routes` + `activeRoute`).** Borrowed from dsh-xdpool's routing page: several models strung into one chain that is tried in your own order instead of being re-decided by the measured score every turn. Two strategies - `fallback` restarts from the head every turn (the first member is the one you put first, and a failure there is a reason to try the second), while `round-robin` starts from a cursor and advances it every `stickyLimit` turns (a multi-turn exchange stays on one upstream while a burst soaks the equivalent lanes). **The model the turn started on always stays first**: a route decides what comes after it, never what replaces it. Members are resolved against the live roster - an id the roster does not list (a hand-typed typo) or one the exclusion lists block is not dispatched and is named as `not dispatched` in the report, rather than silently shrinking into a chain you cannot see.
- **Added: a route editor on the settings page.** Routes used to be a hand-edited `config.json` entry, and *order* is precisely what a text editor is worst at. The editor above the model list now creates, renames and deletes routes, moves a route or a member up and down, switches `fallback`/`round-robin` (with `stickyLimit`), enables or disables one, and marks which is in force. The member box autocompletes from the live roster; an id outside it is still accepted but marked in place. Edits accumulate in a draft and only reach the file on save - a half-arranged table written to disk is the next turn pointed at the wrong model. Deleting the route in force clears `activeRoute` in the same write instead of leaving an orphan name that every report would show as `ignored`.
- **Added: same-model preference became a tier instead of a bonus.** "The same model on another channel" used to be a scoring bonus, so an unrelated model that measured 0.9 outranked a 0.7-scoring twin of the same model - which the reader experiences as "it changed my model for no reason". Ordering now goes by tier first (0 same id on another channel / 1 close relative / 2 shared family stem / 3 unrelated) and only then by score. dsh-xdpool gives the same reason: switching models changes the context window, the tool-calling behaviour, the structured-output shape and the writing style, so a cross-model fallback is a last resort rather than a first one. With `preferSameModel` off every candidate is one tier and the measurements decide again.
- **Added: a breaker (`breakerFailures` / `breakerRestMs`).** The backoff is capped by `maxCooldownMs` (30 minutes by default), which means a route that fails every dispatch returns to the ranking twice an hour, each time costing `retriesPerModel` retries plus the backoff sleeps before the walk moves on. Measured in this install's own `stats.json`: one channel had 493,783 consecutive failures and zero successes. A run of failures now earns one long rest (6 hours by default, never less than `maxCooldownMs`). It is **counted, not read out of the message** - classification is best effort, the counter is measured, so a run we cannot classify still counts.
- **Fixed: four real error sentences that sat unclassified.** Taken from this install's `stats.json`: `Upstream request failed: Model is unavailable` (the aggregate gateway), `codearts: The request param is invalid`, and `请求参数错误…` now read as `unsupported` (a dead route, six-hour rest); `未配置凭据，请先登录` reads as `auth` (retries kept - a re-login really does recover). On the same data the unclassified rows went from 46 to 38; the other 37 are empty messages.
- **Fixed: an empty failure message is no longer recorded as nothing.** An empty message used to be written out as the empty string, so the row was neither classifiable nor re-readable - 37 of 106 rows were exactly that. It now falls back to the finish kind and then to the caller's own label.
- **Tests: routes, the breaker, tiered ordering and the four real sentences all have assertions.** Offline 204 → 222, client 102 → 106 (the routes panel rendering), settings 35.
- **Two test-infrastructure fixes that had been hiding real failures.** (1) Both suites hardcoded the profile at `C:/Users/lenovo/...`, so `createRequire` threw on any other machine and not a single assertion ran; they now resolve through `DSH_HOME` / `DSH_PROFILE_DIR` / `profiles/desktop`. (2) The pin scenario never restored `DSH_MODEL_ROTATOR_CONFIG`, leaving `pin-config-cool.json` behind for every later scenario - so the window guard's own control ("with the guard off the small route is dialed") was running with somebody else's pin, and its failure had nothing to do with the guard.

## 0.2.16
- **New: `model_rotator_status` can clip the ranking (`maxRows`) and collapse the disabled lists (`summary`).** The ranking is one row per discovered route — 488 pairs on this machine — and a single status call produced 69,619 bytes of raw text, roughly 17k tokens, to answer a question that is usually one line. Both controls are optional and `maxRows` defaults to `0` (every row), so no existing behaviour changes.
- **A clip always states what it withheld.** Silent truncation is worse than no truncation: a clipped ranking reads as "these are all the routes", which is exactly the wrong conclusion for someone hunting a model that has gone missing. Whenever rows are cut, a `… N more row(s) withheld` line is appended.
- Offline assertions 198 → 204 (six new: the default clips nothing, a clip states its count, a clip is actually shorter, `maxRows: 0` means all, summary still answers the state question, both controls are declared).

## 0.2.15
- **Fixed: the gateway's "has no provider supported" 400 was classified as nothing, so a permanently dead route kept coming back.** An aggregate gateway answers `400: {"message":"Model id : X , has no provider supported"}` for an id in its catalogue with no backend behind it. `classifyFailureKind` had no pattern for that sentence, so the failure fell through to `''` - the ordinary exponential backoff - which is the wrong shape twice over: the dead route returned to the ranking every cooldown window (30 minutes by default), and every return cost the turn `retriesPerModel` retries plus the backoff sleep before the walk moved on. Observed live on 2026-10-22: `modelscope/deepseek-ai/DeepSeek-V4.1-Flash` reached 24 consecutive failures on this exact sentence while its `lastErrorKind` stayed empty.
- **An `unsupported` route now rests for six hours instead of one cooldown window.** The kind is settled before the model is ever read (no backend behind the id, or a request shape the provider refuses), so it answers identically every time and the backoff shape was the wrong policy for it. `UNSUPPORTED_REST_MS` is the floor; a longer `maxCooldownMs` still wins. Exported as a test seam.
- **A resting row no longer prints an empty reason.** The type column showed `-` next to an active `COOLDOWN`, which read as "no reason on record" - exactly the column a reader checks before switching a model off by hand. It now says `unclassified`.
- Suites: offline 198 (4 new: `13v`-`13y`), client 102, settings 35, pin-cooling, release gate 23.

It now says `(not among the N candidates - ignored)` or `(cooling down - ignored for now)`.

## 0.2.13
- **Fixed: `model_rotator_benchmark` crashed whenever a probed model failed.** The benchmark's failure branch read a variable named `failedBecause` - the name the *walk* uses for its failure text - while the benchmark's own text lives in `failure`. Probing any unhealthy candidate therefore threw `ReferenceError: failedBecause is not defined` instead of reporting the failure, which is precisely the case the tool exists to measure. The value now comes from the local `failure`.
- **Tests: registration is not execution.** The benchmark was asserted to *exist* in the registry and never once called, which is how the above shipped through 192 green assertions. `6b`/`6c` now call it on a failing candidate and require both the summary and the recorded `FAIL`; reverting the fix fails them at once.
- 194 offline assertions, 102 client, 35 settings.
## 0.2.12
- **Fixed: a failover could move a conversation onto a route too small to hold it.** A model can be perfectly healthy and still be the wrong place to continue *this* conversation: the request then overflows the route's context window and the turn dies - and the compaction that could have shrunk the conversation cannot run either, because the summary is requested on that same route. Live case: a conversation ~450k tokens long, running on a 1M-window route, was switched to a route whose window is 262k; from then on every turn ended on `MAX_TOKENS` with a 1-token reply, and eight consecutive compactions failed with "summarization truncated at the token cap". The ranking now drops candidates that cannot hold the conversation as it stands: pressure comes from the host's token meter, the window from the adapter that owns the route (`ctx.llm.resolveModelInfo()` - a profile *declaration* is not a dispatch), and a candidate is held back only when it is smaller than pressure + 32 768. Nothing is rejected on a number the plugin does not have: no pressure reading means no guard, an unpublished window means no opinion, and a route on the same window as the current one is exempt because the guard decides about *moving*. The model list names `window` as the reason, and `model_rotator_status` prints the pressure it acted on.
- **New setting: `windowGuard`** (default on, settings page toggle). Turn it off to make every discovered model a candidate again, whatever its size.
- 192 offline assertions (21a-21g are the new guard cases, including the "guard off", "no reading" and "unpublished window" controls), 35 settings assertions, **102 client assertions**.
## 0.2.11
- **Fixed: the Model switches tab could not tell which conversation it was in.** Both 0.2.9 and 0.2.10 read the id as `sessions.list.getSnapshot().current` - a field that store never carried (it exposes `ids` / `byId` / `phase` / `projectionsBySession`; `current` belongs to the `uiSession` service instead). The tab now declares the Host's own inject contract, `inject: (sessionId) => ({ sessionId })`, and reads `props.sessionId` - the same thing the built-in 对话 and 轨迹 tabs do; the service read is kept only as a best-effort fallback for a Host that injects nothing. Until this, the tab always degraded to the unfiltered log, which is what the reader saw: an empty-state line next to the "conversation not identified" banner.
- 185 offline assertions, **102 client assertions** (6j-6l pin the inject contract and prove an injected id outranks a service-reported one).
## 0.2.10
- **Fixed: a switch was recorded against the wrong conversation.** The 0.2.9 tab files records per conversation, but the owning session was read at the **turn boundary** (`agent/turn-stopping`) while the pending queue is **process-wide**. A conversation whose turn never stops therefore left its switch in that queue, and the *next* conversation to stop a turn drained the batch and stamped it with its own name. Reproduced live: conversation A's switch was filed under conversation B, so A's own tab read "no model switches in this conversation" - history that looks empty. The record is now written **where the switch happens**: the `llm/stream` candidate branch resolves the initiating agent's session through `ctx.get('agents').currentInitiator()` (the same seam adoptServedModel already trusts) and appends at/from/to/purpose/reason with it. The turn boundary now only decides whether to *also* post the in-conversation row.
- **Fixed: a switch with no resolvable session is no longer lost.** A plugin route, or a host without `agents`, has no live turn: the record is still written with an empty session (visible in the every-session view only), without throwing or warning.
- **Fixed: the tab no longer shows "nothing here" over a non-empty log.** When the requested conversation returns zero rows but the log total is not zero, the tab falls back to the full history and says so (new `switches.fallback` copy) instead of claiming there were no switches.
- **Deliberately unchanged**: the log is still in-memory (lost on restart), subagent turns still write no root record, and the every-session view still does no per-conversation isolation.
- 185 offline assertions (scenario 20 rewritten as 20a-20m, adding the cross-talk regression and the no-live-turn case); 99 client assertions.

## 0.2.9
- **New: a switch is recorded on its own tab instead of being spent on context.** The record used to exist only as a notice row inside the conversation, which cost context for a plumbing fact the reader may not have been looking at — and when the row was turned off there was no record at all. Switches now land on a **Model switches** tab beside 对话 / 轨迹 / 上下文, one row each: when, from which model to which, and why. The tab reads the plugin's own log (`GET /_dsh/model-rotator/switches?session=<id>`), so nothing is added to the conversation. Records are filed per conversation — the host hands no session to a plugin route, so the session is bound at the turn boundary, the one moment that both sees the switch and knows whose it was.
- **Changed: the in-conversation row is now opt-in** (`noticeSwitch` defaults to **off**). The tab is the record; turning the setting on additionally posts the old line in the transcript.
- **Fixed: a deterministic dead end no longer asks before switching.** A balance that is gone will not come back inside the 10 s window, and a request the provider refuses as unsupported is refused identically on the next dispatch — declining there could not have kept the model, so the question only cost a card and a wait. `quota` and `unsupported` now switch on their own. **Auth deliberately still asks**: a 403 is often a burst-rate proxy that clears, so keeping the model is a real choice there.
- 179 offline assertions. The dead-end rule has its own negative control: if the gate had simply been removed, the auth assertion would stop asking too. [`12fe8bf`]

## 0.2.8
- **Fixed: the switch notice named the wrong reason.** The line says "A → B", so the reason has to be why A went away — but it was read from the last failure the *walk* saw, which by then belongs to whichever candidate failed just before the winner. With one dead model those are the same string; with two they are not, and a balance wall on the starting model was announced as "(network)" because the channel tried after it had a socket reset. The reason now comes from the starting model's own failure. Observed live on 2026-10-18: 魔塔 was out of balance, nvidia answered, and the notice blamed the network.
- The fallback to the last failure is kept for the case where the starting model never reported one (a host refusal, an aborted turn), so the notice stays populated.
- 169 offline assertions; the negative control reverts to the old source and fails exactly this assertion, reproducing the "(network)" wording. [`79a8d5a`]

## 0.2.7
- **Fixed: a compaction that ran out of quota ended the whole turn.** The compaction summary is the first call a long conversation makes, so when the current model's balance was gone it was the first thing to fail — and it was on the do-not-fail-over list, which meant the refusal was passed straight through and the turn died before the answer existed. Compaction now walks the candidate list like any other dead route: the summary is written by the next model and the turn continues. A session title still stays on the model that was asked, because a caption nobody waits on is not worth a second provider.
- **Fixed: the switch question no longer parks a summary.** Asking "switch model?" before a compaction would have shown a modal about plumbing the reader is not watching, and on timeout it switched anyway. Compaction switches proceed unconfirmed; the reader still learns about it from the ordinary switch notice at the turn boundary.
- **Unchanged on purpose: compaction never adopts the switched model.** A summary that fails because the context is too large for this model says nothing about the model's fitness for the conversation. Adoption is left to the conversation attempt, which makes the same call on the right evidence.
- 168 offline assertions, with three negative controls proving each new exclusion is what makes its assertion pass. [`c5590ef`]

## 0.2.6
- **Fixed: other channels of the same model were deduplicated out of the walk.** This is the real problem 0.2.5 uncovered once the classification was right: when WorkBuddy met its quota wall, **buddy and trae — the same model on other channels — were healthy**, but "one channel per model family" kept them out of the candidate list entirely, so the turn ended on the quota error with a working route sitting one slot away. A family now keeps up to **two channels**: the ranked winner plus one proven-usable backup. A cooling backup is dropped, since dispatching it would walk into the same wall. The switch notice is already deduplicated by model id, so arriving at a second channel of the same model is not announced as "switched to the same model again".
- Measured: before the fix the walk held one channel of `deepseek-v4.1-flash` and `buddy` (ok=1538, healthy) was absent; after it holds three and `buddy` is back. [`fed9508`]

## 0.2.5
- **Fixed: an exhausted quota read as a rate limit, so the switch never happened.** WorkBuddy answers "可用账号均在限流中，最近一个将于 … 解禁" — every account exhausted. Classified as `rate-limit` it cooled for 60 seconds and retried the same wall; one evening accumulated 702 failures. An account pool that is entirely unavailable is now recognised as `quota` and rests like any other balance wall.
- **New: the release time is parsed out of the message.** When the provider states when it comes back, that beats any calendar policy. `parseReleaseTime()` accepts `2026/10/18 00:29:52`, `2026-10-18 00:29:52` and ISO forms; a parsed time becomes the exact cooldown (measured here: 60 seconds became 1.7 hours), and only an unparseable message falls back to the next-day rule.
- **Fixed: a switch was not persisted.** The switch notice was queued and then returned, so `scheduleStatsSave()` never ran — a restart showed the old model still in use. The save happens with the enqueue now.
- **Improved: a pin defers while it cools.** A model pinned with `model_rotator_select` took the head on every turn even while cooling, so every turn opened by walking into the same wall. The pin now applies only while the model is healthy; the ranking decides during cooldown and the pin returns by itself afterwards. [`a2d5a0c`]
